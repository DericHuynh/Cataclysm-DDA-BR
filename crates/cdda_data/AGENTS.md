# cdda_data DOX

## Purpose
JSON loading, definition registry, `copy-from` inheritance resolution, Bevy entity spawning for all game definitions, per-category flag systems, and JSON Schema generation for modder tooling. Owns the pipeline that turns `data/**/*.json` into a queryable `DefinitionWorld` resource.

## Ownership
- Source lives under `crates/cdda_data/src/`. Modules: `loader`, `resolve`, `registry`, `def_world`, `def_registry_resource`, `def_kinds`, `patch`, `populate_flags`, `interner`, `mod_info`, `mod_layer`, `raw_values`, `assets`, `json_asset`, `schema`, `schema_gen`, `flags`, `roundtrip`, `bridge`.
- Bin target: `src/bin/generate_schemas.rs` (invokes `schema::write_all_schemas`).
- Bevy deps (pinned at workspace): `bevy_ecs`, `bevy_app`, `bevy_asset`, `bevy_state`, `bevy_reflect`. Workspace crate deps: `cdda_core_types`, `cdda_components`, `cdda_catalog`, `cdda_defs_raw`. Other: `serde`, `serde_json`, `tracing`, `thiserror`, `schemars`, `indexmap`, `fixedbitset`, `bidimap`. Dev-deps: `tempfile`, `bevy_ecs`, `cdda_components`, `cdda_core_types`.
- Raw data under `data/` is owned by `data/AGENTS.md`; this crate consumes it.

## Local Contracts

- `Loader::load_reported` is the startup/CLI reporting seam: stable discovery, one disk parse per file, reset raw data on repeated loads, category resolution/conversion progress, fatal ingest diagnostics and visible warnings for omitted/unhandled definitions. Existing inspection APIs remain available.
- **Two-pass load contract.** `Loader::ingest_all` (Pass 1) walks `data_dirs`, parses `.json` into `RawDef { id, value, source }` grouped by `"type"`, and applies `default_type_aliases` (e.g. `GUN`/`AMMO`/`COMESTIBLE`/... → `ITEM`) via `canonicalize_types`. `Loader::load` (Pass 2) calls `resolve_all`, which topologically sorts each type by `copy-from` and applies `resolve::resolve_copy_from` (extend / delete / relative / proportional semantics from `patch::apply_cdda_patch`). The final DefRegistry is the typed compatibility/tooling store used by legacy publication; the native runtime catalog is separate.
- **Asset-loader seam (`Loader::ingest_values` / `Loader::resolve`).** The Bevy asset pipeline (`json_asset.rs` parses one `.json` file into `CddaJsonFile { values: Vec<Value>, source }`; `cdda_app::data_assets` loads per-file assets via the asset server) cannot walk directories from a `LoadContext`, so `ingest_values(&mut self, Vec<(PathBuf, Vec<Value>)>)` feeds already-parsed values into the same raw-def map as `ingest_all`, and `resolve()` runs Pass 2 only. The reported disk path (`load_reported`) and the asset path (`ingest_values`+`resolve`) therefore produce identical registries; this is pinned by the `asset-loader seam` tests in `tests/hot_reload_test.rs`.
- **Macro-driven resolve dispatch.** `resolve_all` and `log_skipped_types` are driven by `for_each_raw_def_kind!(call ...)` — the `(Name, DefType, json_type, field, strategy)` table is the single source of truth for which `resolve_type_with_pipeline::<DefType>(json, &mut registry.field, errors)` call runs and which type strings count as handled. Adding a category no longer requires hand-editing ~440 lines of resolve calls or the skipped-type literal; only the table row plus the `DefRegistry` struct field. `mapgen` (and its `nested_mapgen` variant) stay special-cased (`resolve_mapgen`); `mapgen` is added to the handled-type set manually.
- **Raw-map keying (`build_raw_map`).** Correctly mirrors CDDA identity so every `copy-from` target resolves:
  - **Recipes** are keyed by their composite id — `result` plus an `id_suffix` **or** a `variant` (`herbal_tea` + `from_tea_bag` → `herbal_tea_from_tea_bag`). A recipe variant that `copy-from`s its own composite key is skipped so it doesn't clobber the base or self-cycle. The final registry insert PRESERVES the composite key for recipes (`resolve_type_with_pipeline` special-cases `type_name == "recipe"` to use the raw-map key, not `extract_def_id`'s bare-`result` fallback) — different recipes producing the same item no longer overwrite each other. Pinned by `recipe_variant_identity_does_not_collapse` in `loader.rs`.
  - **Named abstracts** (no `result`/`id`, identifier in the `abstract` string) are keyed by that string.
  - **Array-valued `id`**s register *every* element (e.g. `corpse_bowels_*` multi-id defs), so any element is a valid `copy-from` target.
- **Round-trip seam (Phase A).** `roundtrip.rs` proves the JSON→struct→JSON seam is lossless. `Loader::resolve_type_raw(json_type)` runs the same copy-from/abstract resolution as `resolve_type_with_pipeline` but returns the **final resolved raw JSON** (`Vec<(id, Value)>`) without typed deserialization. `roundtrip::roundtrip_all_types(&loader)` dispatches over every `for_each_raw_def_kind!` category and checks each def's resolved JSON re-parses into its typed struct with **no fields dropped**. The comparator tolerates serde's legitimate re-encoding (typed unit newtypes like `Volume(250)` vs `"250 ml"` via quantity canonicalization, `DefId<T>` wrapper nesting) and allowlists intrinsic metadata (`type`, `abstract`, `copy-from`). It reports *unmodeled* CDDA fields as findings (project hasn't modeled the full schema) and treats *parse failures* + *unresolved defs* as real problems.
- **CLI driver.** `cdda-cli roundtrip <dir>` prints the per-category report; `--strict` exits 1 on parse failures/unresolved. Tests: `tests/roundtrip_resolved.rs` — a deterministic fixture (copy-from + unit strings must be lossless) plus a real-`data/core` diagnostic report.
- **`DefRegistry` god object.** Single struct with ~100+ `HashMap<DefId<T>, Arc<TDef>>` fields (one per category). `for_each_raw_def_kind!` (in `def_kinds.rs`) is the single source of truth for the `(name, DefType, "json_type", field, strategy)` table. `DefRegistry::total_count` and `category_count` are macro-generated from that table (`for_each_raw_def_kind!(call ...)` inside each method), so adding a category no longer requires hand-editing the counters — only the table row plus the struct field. `mapgen`/`nested_mapgen` are special-cased (String-keyed, not in the table). `DefRegistry::empty` still hand-lists every field (Rust can't macro-iterate named typed fields of distinct types). Native runtime contracts move to cdda_catalog through explicit translators; the compatibility registry remains available to import/tooling consumers.
- **Monster combat projection:** MonsterStats.dodge comes from resolved JSON dodge (default zero), independently of melee dice. Definition components remain projections for adapters; runtime MeleeCapability/DodgeDefense/IntrinsicArmor are separate construction outputs. No broad monster behavioral parity is implied.
- **Def-world construction.** `build_def_world(world, &DefRegistry, spawn_all)` (in `def_world.rs`) spawns definition entities into the main Bevy `World` marked with `IsDef`, then returns a `DefinitionWorld` index. It first **despawns every existing `IsDef` entity** so the definition set is *replaced*, not accumulated, across hot reloads (gameplay entities must never carry `IsDef`). Per-category builders exist: `build_item_defs`, `build_monster_defs`, `build_terrain_defs`, `build_furniture_defs`, `build_recipe_defs`, `build_body_part_defs`. `spawn_all=false` skips everything except body parts. Decomposition into more granular per-category functions is the active debt item.
- **`DefinitionWorld` resource.** Typed index `HashMap<(DefCategory, String), Entity>` (`Item/Monster/Terrain/Furniture/Recipe/BodyPart`) plus a legacy flat ITEM lookup (`entity_by_str` — items only) and a `generation` counter bumped on every `build_def_world` rebuild so runtime caches can detect staleness and re-resolve. Same-text IDs across categories coexist; flags population and the HTN catalog resolve per category. Recipe defs register under their resolved composite key and carry it as `DefStrId` (runtime references re-resolve by stable identity, not pre-reload `Entity`). Public API: `empty`, `entity_by_str`, `entity_in(category, id)`, `generation`, `len`, `is_empty`, `iter` (yields `(DefCategory, &str, Entity)`); `register` is public for projection adapters; the index and interners are owned by cdda_catalog and re-exported here. Generation-aware migration of ALL cached definition entities remains tracked debt.
- **`DefRegistryResource(Arc<DefRegistry>)`** wraps the resolved registry as a `bevy_ecs::Resource` for runtime tools (e.g. registry viewer). Separate from `DefinitionWorld`, which is the entity index.
- **Mod layering (APPLIES the mods).** `mod_info.rs` defines `ModInfo`, `ModId`, `ModError`, `check_dependencies`, `check_conflicts`, `resolve_load_order` (Kahn's algorithm). `mod_layer.rs` adds `ModManager { available, core_registry, core_loader }`, `ModLoadResult`, `ModManifest`, `topological_sort`, `check_conflicts`, `load_mods(&mut self, …)`, and the headless `load_with_mods`. `load_mods` ingests each mod's directory into the SAME loader that retains the core raw defs (`Loader::ingest_dir` — the mod-layering seam, returning only the newly ingested defs) and then RE-RESOLVES the accumulated raw set: the returned `ModLoadResult.registry` for mod *N* is core + mods 1..=N, layered last-write-wins per ID, with mod defs able to `copy-from` core or earlier-mod defs (copy-from resolves against the LAYERED parent). (This fixed the old behavior that ingested mod data but returned a clone of the untouched core registry.) No separate `ModShard` numeric space exists yet. Pinned by the `load_mods_applies_mod_definitions_over_core` / `layered_registries_accumulate_in_dependency_order` tests in `mod_layer.rs`.
- **Schema generation split.** `schema.rs` produces static JSON Schema files per type via `schemars` (`write_all_schemas`, `validate_against_schema`, `validate_all`). `schema_gen.rs` produces dynamic schemas with runtime-injected `enum` values for flags and IDs: defines `ModRegistry { all_flags, all_item_ids }`, `ItemModSchema`, `CddaSchemaPlugin`, `collect_mod_registry_v2`, `generate_dynamic_schemas`, and `generate_schemas_for_mod` (headless CLI path). Output dir resolved by `schema_output_dir` (`assets/schemas` or `$CARGO_MANIFEST_DIR/../../data/schemas`).
- **`htn_compound` defs.** Data-authored HTN compound tasks (`"type": "htn_compound"`, see `cdda_defs_raw/src/raw_defs/htn.rs`) are a standard def kind (table row + `DefRegistry.htn_compounds`). Unlike item/monster defs they get NO def-world entities: the HTN domain compiler (`cdda_sim::ai::htn::compile_domain`) consumes a native HtnSource translated from the registry and bakes them into a `cdda_htn` domain — `def_world.rs` deliberately has no builder for them (same spirit as `mapgen`'s special casing). Schema: `data/schemas/htn_compound.schema.json`.
- **Flag system.** `flags.rs` defines `FlagMap` (bidirectional string↔`u16` map, cap 4096), per-category `*FlagRegistry` Bevy `Resource`s, and per-category `*Flags(FixedBitSet)` components. `CddaDataPlugin` initializes all registries. `populate_flags::populate_def_flags` runs after `build_def_world` and inserts the bitset component on each entity. `register_flags_from_json` mirrors the C++ `auto_flags_reader` (handles array, single-string, `extend`, `delete`).
- **Patch semantics.** `patch::apply_cdda_patch` mirrors C++ `generic_factory`: nested objects recurse, arrays replace, scalars replace. `extend` appends to an existing array field (no-op with warning if absent — never creates the field). `delete` removes matching elements (no-op with warning if absent).
- **Integer-safe relative / proportional.** `resolve::apply_relative` / `apply_proportional` preserve integer-ness: when the current value is an integer (CDDA int attribute like `damage`/`range`/`recoil`), the result is emitted as an integer rounded to nearest — no FP noise like `825.0000000000001` — so resolved JSON stays deserializable into `i32`/`u64` fields. `clean_float` snaps non-integer results to a bounded number of decimals.
- **Named abstracts get an id.** `resolve::resolve_copy_from` promotes `"abstract": "some_id"` (a named abstract whose identifier lives in the `abstract` field) to `id` during resolution, since `apply_definition` strips the `abstract` key. The boolean template form (`"abstract": true`) never gets an id. This keeps named-abstract defs deserializable.
- **Part-B bridge (import/export adapters).** `bridge.rs` treats the **fully-resolved raw JSON** (the output of `Loader::resolve_type_raw`/`resolve_type_raw_with_parent`) as the lossless source of truth and provides decoupled import/export adapters for a future GUI editor and format migrations. Import (`import_def`) wraps a resolved `Value` + typed parse in a `DefRecord<T>` Bevy `Component` (raw never dropped, so unmodeled keys survive); export (`compute_overrides` + `apply_delta` + `export_override_def`) computes the *minimal* `copy-from` override delta against a def's parent — fields equal to the parent are omitted (inherited defaults write nothing), brand-new fields are added, removed inherited fields become `delete`, and differing nested objects/arrays override wholesale (CDDA merges one level only). `Loader::resolve_type_raw_with_parent` surfaces the raw `copy-from` linkage per def (resolution strips the key), which `bridge_all_types` uses to verify every modeled `copy-from` def round-trips: `apply_delta(parent, compute_overrides(parent, child)) == child`. Import/export share no state: a new wire format only needs a new adapter, never a rewrite of the other direction.

## Native inventory seam
- `inventory_import` consumes ordered SourceDocuments without I/O, retains original/resolved values and provenance, and reports Supported / PreservedUnimplemented / Rejected. Strict access fails on unsupported or rejected content. Supported family: counted generic items, unrestricted container pockets, qualities and counted recipes. This is separate from broad legacy app loading.
- `inventory_publish` validates before changing resources/entities, then replaces its native definition set. Mixing legacy publication is rejected. ItemDefinitionRef and PreparedItem snapshots retain their old data. General actor/AI reference migration and native game saves remain deferred.
- `Loader::keyed_sources` shares resolution identity rules; raw resolution preserves recipe composite and multi-ID keys. Aliases canonicalize at ingestion to preserve last-writer order.
- `cargo run -p cdda_data --example inventory_compat -- <core path> [mod path ...]` reports native-family capabilities read-only. Inputs are explicitly ordered; this is not a full-game support claim.

## Work Guidance
- Keep the three concerns separated: parse (`Loader`) → resolve (`resolve`) → spawn (`build_def_world`). Don't re-introduce I/O in resolve or registry mutation in spawn.
- When adding a new def category: extend `def_kinds.rs` (one `for_each_raw_def_kind!` line, which now also auto-wires `total_count`, `category_count`, `resolve_all`, and `log_skipped_types`), add the `HashMap` field to `DefRegistry` and to `DefRegistry::empty` (the only hand-maintained counter list, since Rust can't macro-expand named typed fields of distinct types), and add a per-category builder in `def_world.rs` (or wire it into an existing one). New flag categories also need a `flag_registry!` + `flag_comp!` pair in `flags.rs` and a registry init in `CddaDataPlugin`.
- `Loader` is mutable because pass-1 ingestion mutates `raw_by_type`. `ingest_all` is useful when you want raw defs without resolving (e.g. schema tooling that needs pre-resolution flag/ID discovery).
- `resolve::topological_sort` is the cycle detector; `LoaderError::CircularCopyFrom` and `MissingCopyFromTarget` come from there. `ModError::CircularDependency` and `UnknownDependency` are independent mod-graph errors.
- Mods re-parse the same JSON format as core data — no separate schema. Manifest discovery handles both `modinfo.json` and `mod.json`. `try_load_manifest` is the single ingestion point.
- Schema tools should write to the path returned by `schema_output_dir`; modder-facing schemas live at `data/schemas/*.schema.json` (referenced by `"$schema"` in mod JSON, which the loader tolerates).

## Verification
- `cargo check -p cdda_data` for compile sanity.
- `cargo nextest run -p cdda_data` (fall back to `cargo test -p cdda_data` if `nextest` is unavailable) covers the per-module test suites: loader ingest/canonicalize + raw-map keying (recipe composite-id, variants, named-abstract, array multi-ids), `resolve` copy-from operations (extend/delete/relative/proportional/cycle, plus the integer-safe proportional/relative and named-abstract-id regressions), `patch` semantics, `flags` `FlagMap`, `populate_flags` no-panic, `def_world` per-builder empty-registry tests, and `schema` / `schema_gen` enum-injection and `$schema` tolerance.
- `cargo run -p cdda_data --bin generate_schemas` to regenerate static schemas into `data/schemas/`.
- `cargo run -p cdda-cli -- check data/core` for end-to-end data validation against the live CDDA JSON set.
- `cargo run -p cdda-cli -- roundtrip data/core` for the Phase-A JSON→struct→JSON drop check; `--strict` to fail on parse/unresolved. `cargo test -p cdda_data --test roundtrip_resolved` runs the deterministic fixture + real-data report.
- `cargo run -p cdda-cli -- bridge data/core` for the Part-B export-adapter round-trip; `--strict` to fail on export mismatches. `cargo test -p cdda_data --test bridge_resolved` runs the deterministic fixture + real-data gate (zero mismatches). `cargo test -p cdda_data --lib bridge` runs the adapter unit tests.
- **Hot reload is tested end-to-end** via `cargo test -p cdda_data --test json_asset_hot_reload`. It builds a real Bevy `App` (a watched `cdda` asset source backed by `MemoryAssetReader` + an injectable `AssetWatcher` event sender), loads existing JSON as a `CddaJsonFile`, replaces the file's content, emits `AssetSourceEvent::ModifiedAsset`, and asserts the asset server automatically re-parses the new JSON and that `Loader::ingest_values` + `resolve` turn it into a registry reflecting the new definitions (added/removed) — the same seam `cdda_app::data_assets::reload_modified_data` uses at runtime. The pure-Loader seam (`ingest_values` + `resolve` copy-from / type-alias) is pinned separately in `tests/hot_reload_test.rs`.
